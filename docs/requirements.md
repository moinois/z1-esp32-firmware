# Requirement traceability

This file records implementation and verification separately. An implementation
claim means that the production composition exists and the ESP-IDF target builds;
it does not imply physical conformance. A requirement is physically conformant
only when the final column contains a reviewed `HIL PASS` or says that hardware
verification is not required.

Normative requirement IDs link to the current public specification on GitHub.
Release conformance reports shall instead record the exact specification commit
so their meaning cannot change when the specification advances. IDs prefixed
with `PROJ-` are local backlog requirements until matching normative text has
been accepted into the specification.

Physical tests live under `tests/hardware` and follow
`docs/hardware-testing.md`. Their result vocabulary is `PASS`, `FAIL`, and
`SKIP`; only a reviewed `PASS` is physical evidence. Test availability or a
`SKIP` does not change the entries below. The initial HIL suite can exercise
[USB-001](https://github.com/f355/esp32_cnc_spec/blob/main/02-framing-and-transports.md#usb-001)--[USB-005](https://github.com/f355/esp32_cnc_spec/blob/main/02-framing-and-transports.md#usb-005), [USB-009](https://github.com/f355/esp32_cnc_spec/blob/main/02-framing-and-transports.md#usb-009), [TCP-001](https://github.com/f355/esp32_cnc_spec/blob/main/02-framing-and-transports.md#tcp-001)--[TCP-004](https://github.com/f355/esp32_cnc_spec/blob/main/02-framing-and-transports.md#tcp-004), [SD-001](https://github.com/f355/esp32_cnc_spec/blob/main/06-storage-and-configuration.md#sd-001),
[FILE-020](https://github.com/f355/esp32_cnc_spec/blob/main/06-storage-and-configuration.md#file-020)--[FILE-026](https://github.com/f355/esp32_cnc_spec/blob/main/06-storage-and-configuration.md#file-026) when the required fixtures are found. Diagnostic-port
discovery is a fixture check and does not by itself verify LOG or DIAG behavior.
No physical result is claimed merely because those tests exist.

Status vocabulary used below:

- `Host-tested`: portable behavior passed the dependency-free C++ suite.
- `Target-built`: the production ESP-IDF composition compiled successfully.
- `HIL implemented`: an executable hardware test exists but has not passed on
  the required fixture.
- `HIL PASS YYYY-MM-DD`: reviewed physical evidence exists.
- `Pending implementation`: production integration is absent or incomplete.
- `Pending fixture`: implementation and automated logic exist, but the required
  physical equipment is unavailable.

Current known production-integration gaps are concentrated in the encrypted
BLUFI provisioning flows, the explicitly noted controller command-family gaps,
and the configuration web interface. Most other open items are physical or
stress verification rather than missing portable logic.
