# Requirement traceability

This file records implementation and verification separately. An implementation
claim means that the production composition exists and the ESP-IDF target builds;
it does not imply physical conformance. A requirement is physically conformant
only when the final column contains a reviewed `HIL PASS` or says that hardware
verification is not required.

Normative requirement IDs link to the current public specification on GitHub.
Release conformance reports shall instead record the exact specification commit
so their meaning cannot change when the specification advances. IDs prefixed
with `PROJ-` are local backlog requirements until matching normative text has
been accepted into the specification.

Physical tests live under `tests/hardware` and follow
`docs/hardware-testing.md`. Their result vocabulary is `PASS`, `FAIL`, and
`SKIP`; only a reviewed `PASS` is physical evidence. Test availability or a
`SKIP` does not change the entries below. The current fixture-gated HIL coverage
is summarized per requirement below and documented in `docs/hardware-testing.md`.
Diagnostic-port discovery is only a fixture check and does not by itself verify
LOG or DIAG behavior. No physical result is claimed merely because a test exists.

## Current portable verification snapshot

As of 2026-08-11, the dependency-free C++ host suite contains 785 passing
tests. The focused suites cover malformed AVI preview inputs, transfer setup,
retry, timeout, sequence, and path failures, CANopen RPDO/TPDO boundary
behavior, filesystem-command failures, and storage-retention failure paths.
The corresponding coverage report is 96.74% lines (7885/8151), 99.01%
functions (800/808), and 86.93% branches (3260/3750). These figures are
portable-test evidence only; they do not replace physical SD, camera, CAN,
controller, or endpoint fault-injection fixtures.

Status vocabulary used below:

- `Host-tested`: portable behavior passed the dependency-free C++ suite.
- `Target-built`: the production ESP-IDF composition compiled successfully.
- `HIL implemented`: an executable hardware test exists but has not passed on
  the required fixture.
- `HIL PASS YYYY-MM-DD`: reviewed physical evidence exists.
- `Pending implementation`: production integration is absent or incomplete.
- `Pending fixture`: implementation and automated logic exist, but the required
  physical equipment is unavailable.

Current known production-integration gaps are concentrated in the explicitly
noted controller command-family gaps. CANopen heartbeat/error diagnostics and
the configuration web interface are now implemented; most other open items are
physical, fault-injection, visual-browser, or endurance verification.

User-controlled filesystem paths are intentionally sandboxed below `/sd` as
documented in [ADR-016](architecture-decisions.md#adr-016). This is a local
security/design decision and must not be mistaken for an upstream specification
change; conformance claims for path syntax are recorded separately from the
authority boundary.
