# GitHub CI and release builds

The repository has two GitHub Actions workflows. They use the same build
scripts as local development; a release is not required to validate a pull
request or a push to `main`.

## Continuous integration

`.github/workflows/ci.yml` runs for pushes to `main`, all pull requests, and a
manual `workflow_dispatch`. It contains two independent jobs:

* **Host tests and coverage** installs Clang/LLVM, CMake, and Ninja, runs
  `python3 tools/host_coverage.py` (the complete C++ host suite), runs
  `python3 -m pytest tools/tests -q`, and uploads the HTML/JSON coverage
  directory as a 14-day artifact.
* **ESP-IDF firmware build** runs in `espressif/idf:v5.4.1` and builds both
  the live profile (`--live`) and the all-mock development profile
  (`--mock-all`). Each job uploads `project_description.json` and
  `hardware-selection.json` as a 14-day artifact.

The workflow is intentionally validation-only: it does not flash hardware,
publish a release, or push branches. Re-run it from the Actions page with
**Run workflow** when a local toolchain is unavailable.

The equivalent local commands are:

```sh
python3 tools/host_coverage.py
python3 -m pytest tools/tests -q
source /path/to/esp-idf/export.sh
python3 tools/build_firmware.py --live --build-dir build-ci-live
python3 tools/build_firmware.py --mock-all --build-dir build-ci-mock
```

## Published releases

`.github/workflows/release-firmware.yml` runs only when a GitHub Release is
published. The release tag must match `vMAJOR.MINOR.PATCH`; each component is
encoded into one byte and passed to `--mainboard-version` as aggregate package
metadata. The workflow then:

1. checks out the immutable release tag;
2. runs host tests and publishes the coverage report to the `coverage` branch;
3. builds a live, non-mock release with `--release` using ESP-IDF 5.4.1 and
   the specification partition table;
4. creates the aggregate `firmware.bin` package;
5. attaches the application image, aggregate package, hardware-selection
   manifest, and `SHA256SUMS.txt` to the GitHub Release.

The release workflow also uploads a 30-day coverage artifact. The README
coverage badge reads `coverage/badge.svg`, which is generated by the workflow;
the percentage is therefore not edited manually.

Release builds are live-only and use the repository `webui` tree. The local
`--alt_webui` option is deliberately not used by CI because `webui-alt` is an
ignored, potentially copyrighted investigation tree. See
[`tools/README.md`](../tools/README.md) for all build switches and partition
selection.

## Build profiles and partitions

`tools/build_firmware.py` writes an auditable `hardware-selection.json` file.
Development builds use `partitions-dev.csv`; release builds use the normative
`partitions.csv`. `--compact` is an experimental size-reduction profile and
is valid only together with `--release`; it is not enabled by either GitHub
workflow. `--mainboard-version` is package metadata and does not change the
human-readable firmware version returned by the device.
