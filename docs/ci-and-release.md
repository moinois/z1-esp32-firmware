# GitHub CI and release builds

The repository has two GitHub Actions workflows. They use the same build
scripts as local development; a release is not required to validate a pull
request or a push to `main`.

## Continuous integration

`.github/workflows/ci.yml` runs for pushes to `main`, all pull requests, and a
manual `workflow_dispatch`. It contains two independent jobs:

The first-party actions use their Node.js 24-based releases
(`actions/checkout@v7`, `actions/upload-artifact@v7`, and, in the release
workflow, `actions/download-artifact@v8`), avoiding the deprecated Node.js 20
action runtime.

The host job installs the distribution `python3-pytest` package explicitly;
`python3 -m pytest tools/tests -q` therefore does not depend on a preinstalled
runner module or on pip network access.

* **Host tests and coverage** installs Clang/LLVM, CMake, and Ninja, runs
  `python3 tools/host_coverage.py` (the complete C++ host suite), runs
  `python3 -m pytest tools/tests -q`, and uploads the HTML/JSON coverage
  directory as a 14-day artifact.
* **ESP-IDF firmware build** runs in `espressif/idf:v5.4.1` and builds both
  the live profile (`--live`) and the all-mock development profile
  (`--mock-all`). Each job uploads `project_description.json` and
  `hardware-selection.json` as a 14-day artifact.

The workflow is intentionally validation-only: it does not flash hardware,
publish a release, or push branches. Re-run it from the Actions page with
**Run workflow** when a local toolchain is unavailable.

The equivalent local commands are:

```sh
python3 tools/host_coverage.py
python3 -m pytest tools/tests -q
export ESP_IDF_DIR="${ESP_IDF_DIR:-$HOME/.espressif/v5.4.4/esp-idf}"
source "$ESP_IDF_DIR/export.sh"
python3 tools/build_firmware.py --live --build-dir build-ci-live
python3 tools/build_firmware.py --mock-all --build-dir build-ci-mock
```

The CMake `host-tests-release` preset is available for an optimized portable
regression run, but CI intentionally keeps the ordinary host test and coverage
profiles separate. It is invoked with:

```sh
cmake --preset host-tests-release
cmake --build --preset host-tests-release
ctest --preset host-tests-release
```

This preset must not be confused with the ESP32 `--release` build flag: it only
sets `CMAKE_BUILD_TYPE=Release` for host C++ tests.

The macOS presets set `CMAKE_OSX_SYSROOT` to the Command Line Tools SDK so the
system libc++ headers are available to Apple Clang. A missing SDK indicates a
local Xcode Command Line Tools installation problem, not a project dependency;
repair the tools installation before running the presets.

The firmware helper resolves an activated ESP-IDF installation from the local
`IDF_PATH` and `IDF_PYTHON_ENV_PATH` variables. It invokes
`$IDF_PYTHON_ENV_PATH/bin/python $IDF_PATH/tools/idf.py` when `idf.py` is only a
shell function, so the installation path does not need to be hard-coded.

## Published releases

`.github/workflows/release-firmware.yml` is started manually with a SemVer
version (without a leading `v`) and a source branch, tag, or commit. It follows
the same staged release model as the Fusion plugin: release publication is
disabled by default, the selected source is resolved to an immutable commit,
and GitHub Release creation is the final step after all verification succeeds.

The workflow validates that the version and prospective `vVERSION` tag are
available. Each numeric version component must fit in one byte and is encoded
for `--mainboard-version`; prerelease identifiers and build metadata do not
alter those three firmware version bytes. The workflow then:

1. checks out the validated source commit for every build and test job;
2. runs host tests and generates the coverage report;
3. builds a live, non-mock release with `--release` using ESP-IDF 5.4.1 and
   the specification partition table;
4. creates and checksum-verifies the aggregate `firmware.bin` package and all
   release assets;
5. uploads firmware and coverage as workflow artifacts; and
6. for a non-dry-run only, publishes coverage and creates `vVERSION` at the
   validated commit with the verified assets attached.

A SemVer prerelease is always published as a GitHub prerelease. A stable
version selected from a ref other than `main` is also classified as a
prerelease unless `publish_stable_from_non_main` is explicitly enabled. Use a
dry run first by leaving `publish_release` unchecked. This exercises the
complete build and packaging path without creating a tag, release, or
coverage-branch update. Check it only when a tag and release shall be created.

The release workflow also uploads a 30-day coverage artifact. The README
coverage badge reads `coverage/badge.svg`, which is generated by the workflow;
the percentage is therefore not edited manually.

Release builds are live-only and use the repository `webui` tree. The local
`--alt_webui` option is deliberately not used by CI because `webui-alt` is an
ignored, potentially copyrighted investigation tree. See
[`tools/README.md`](../tools/README.md) for all build switches and partition
selection.

## Build profiles and partitions

`tools/build_firmware.py` writes an auditable `hardware-selection.json` file.
Development builds use `partitions-dev.csv`; release and ordinary specification
builds use the normative `partitions.csv`. Release images must fit its original
OTA slot size. The standard `--release` profile includes the production-safe
size reductions required for that limit; `--compact` is an optional, auditable
extension and is not required for a valid release. The pull-request CI builds
the regular live profile as an additional size/regression signal. `--mainboard-version`
is package metadata and does not change the
human-readable firmware version returned by the device.

The development table is not an OTA-compatible substitute for the normative
table. Moving a device between development and release layouts requires one
full USB/serial flash to install the matching partition table; different
offsets may erase or make existing data unavailable. CI builds both profiles,
while the published release workflow uses only the live release profile.
